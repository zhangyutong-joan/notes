# 缓存一致性

## 定义
缓存一致性是指在多轮对话或多次 API 调用之间，保持输入消息序列前缀的字节序列完全不变的能力。它是 [[concepts/KV-Cache|KV-Cache]] 和 [[concepts/Prompt-Cache|Prompt-Cache]] 能够跨请求、跨会话复用缓存计算结果的必要条件。由于缓存机制只识别完整的字节序列前缀，任何对消息序列头部哪怕一个字节的修改，都会导致缓存失效、重新计算。

## 关键特征
- **字节级敏感**：缓存的命中判定以原始字节流为准，与语义无关；即使逻辑相同但序列化方式不同，也无法复用。
- **强约束架构**：为了保证缓存命中，Agent 系统的提示词设计、子 Agent 调用、工具结果替换等都必须严格保持前缀不变。
- **反向主导设计**：缓存一致性的性能/经济诉求先于业务逻辑，上下文工程的决策顺序变为“先确定缓存边界，再组织语义逻辑”。
- **跨会话持久化**：不仅适用于单次对话内的多次生成，也适用于跨会话的缓存复用，要求前缀在会话间也保持一致。
- **冻结机制**：部分场景下，工具调用返回的替换字符串在首次生成后即被冻结，后续会话中必须复用完全相同的字节序列来保证缓存命中。

## 应用
- **系统提示词拆分**：将长系统提示词按缓存边界切分为固定前缀部分和可变部分，使固定部分始终命中 [[concepts/Prompt-Cache|Prompt-Cache]]。
- **子 Agent 对齐**：父 Agent 在构建子 Agent 调用时，必须保证传递给模型的完整前缀与子 Agent 训练/配置时的缓存键逐字节匹配，以避免缓存失效。
- **工具结果冻结**：在 Agent 工作流中，首次调用工具返回的结果被序列化为固定的字节块，并在后续反复使用的上下文中原样复用，从而持续命中缓存。
- **上下文工程决策**：工程师在组织对话逻辑时，优先确定哪些部分可以形成稳定的前缀，再围绕这些边界设计语义内容，以降低 token 成本与延迟。
